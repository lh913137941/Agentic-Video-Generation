# 单页对话式创作工作台设计（2026-10-10）

> 参考：项目现有 vLLM-Omni 设计文档、docs/ui_workflow.md，以及用户提供的即梦 AI 创作页与当前 UI 截图。借鉴其“统一输入框 + 技能入口 + 连续创作”的布局逻辑，不连接即梦服务，也不复制账号、商品、未实现的 Agent 能力。

## 1. 现有问题与目标

先前两个顶层 Tab 分别承载「视频智能编辑」和「剧本成片」，让用户在一个视频项目里反复切换页面。虽然已把模板下拉框变成卡片，首屏仍是两个独立表单：用户先决定功能页，再上传/写作，再跳转结果。项目上下文被功能边界割裂。原先的大 Hero 也挤压了真正重要的创作入口。

**目标：一个工作台、一处核心创作输入、两项现有技能、同一页面查看过程与资产。** 顶部紧凑品牌栏，中央创作框聚合 MP4 上传、Prompt、技能选择、提交；下方动态显示任务事件、生成结果、镜头卡片。两类任务不是两个网页，技能切换仅更改当前上下文，不丢弃本次会话中的另一类结果。

必须坚持能力边界：这里的“对话”是提交动作和任务状态的展示，不是已实现的自然语言 Agent、多轮自动规划；用户明确选择任务类型，不使用关键词或 LLM 暗中路由。

## 2. 统一页面结构

- 顶栏：Agentic Video Studio 名称、MVP 标记；缩短上版大幅营销 Banner。
- 核心区域：中心大创作框。左侧 MP4 附件上传，右侧唯一主 Prompt；底部真实技能按钮「视频编辑」「创作分镜」及统一生成按钮。
- 次要配置：折叠的快速模板（黄昏、物体替换、删除物体、推镜）及全片风格、分镜数量、重新检测。模板直接填入 Prompt 并选择视频编辑技能，不提交推理任务。
- 项目工作区：左边任务对话/状态事件，右边当前结果（视频编辑原片 vs 结果；或粗剪），如果当前是分镜项目则自然展开镜头卡片并支持局部重投。
- 不展示未实现的技能为可执行操作：视频反解、风格大师、Agent 技能管理、区域 Mask、精确时间选区是下一阶段候选。

简图：

    ┌─ 顶部品牌 / 当前版本 ──────────────────────────────────┐
    │                     今天想创作什么？                   │

    │ │ [＋ MP4 附件] [主输入框：意图/剧本/编辑指令]     │   │
    │ │ [视频编辑] [创作分镜]        [开始生成 →]         │   │
    │ └──────────────────────────────────────────────────┘   │

    │ 当前创作项目                                           │
    │ [动作/状态时间线] [编辑前后对比 或 粗剪视频]            │
    │                 [分镜资产卡片/单镜头重投]               │
    └────────────────────────────────────────────────────────┘

## 3. 前端状态（会话）与显式路由

当前代码：src/agentic_video/workspace.py。使用一份浏览器会话状态，不是新的后端 Project 类型：

| 字段 | 含义 |
|---|---|
| mode | 当前明确选择的技能：video_edit 或 storyboard |
| active | 当前结果区展示的视频编辑结果或分镜项目 |
| source_name | 上传视频的显示名，不代表外部可访问文件 |
| edit_job | 最近一次视频编辑任务的后端快照 |
| story_project | 最近一次分镜工程的后端快照 |
| timeline | 用户动作与任务状态变化，最多保留 30 条 |

UI 控件事件：

| 事件 | 前端编排 | 后端接口 |
|---|---|---|
| 上传 MP4 | 选择“视频编辑”、增加已上传事件 | 此时不提交任务 |
| 点击视频编辑 | 选择 V2V 模式与结果区上下文 | 无 |
| 点击创作分镜 | 选择 Script-to-Rough-Cut 上下文 | 无 |
| 点击编辑模板 | 填充主 Prompt、切换到“视频编辑” | 无 |
| 视频编辑提交 | 文件 + Prompt 且后端支持才提交 | POST /api/video-edits |
| 分镜提交 | 剧本 + 风格 + 分镜数；不得携带被静默忽略的视频 | POST /api/projects，POST /api/projects/{id}/generate |
| 状态刷新 | 轮询进行中的任务，变化时增加一条状态事件 | GET /api/video-edits/{id} 或 /api/projects/{id} |
| 目标镜头重投 | 编辑目标镜头，然后只对该镜头发起生成 | PATCH /api/projects/{id}/shots/{shot_id}，POST /api/projects/{id}/shots/{shot_id}/regenerate |
| 视频下载 | 真实完成后才展示下载链接 | GET /api/video-edits/{id}/result?download=1 或 /api/projects/{id}/video?download=1 |

核心路由伪代码：

    action = plan_submission(selected_mode, source_mp4, prompt, count, capabilities)
    if action == "video_edit":
        result = POST /api/video-edits (multipart: file + prompt)
    else:
        project = POST /api/projects (script + theme_style + shot_count)
        result = POST /api/projects/{id}/generate
    workspace = begin_submission(workspace, action, result)
    # Timer 根据任务状态更新 UI 事件及结果，不重写后端任务调度

**重要约束：** MP4 上传默认激活视频编辑；如果用户随后选“创作分镜”并提交时仍携带视频，明确提示当前分镜 API 不会消费这个视频，要求移除附件或切回视频编辑。不能偷偷把视频当作分镜参考，也不能无提示忽略。默认 Mock 可以验证分镜链路，但禁用真实视频智能编辑。Omni 已配置不等于 V2V 模型具备真实能力。

## 4. 状态、错误、恢复与安全边界

- 当前 API 未连接：禁用提交，允许修改草稿并重新检测。
- Mock 模式：创作分镜可提交；视频编辑提交禁用，提示部署支持 V2V 的后端。
- 工作中：同类型任务禁止重复提交；UI 切到另一技能仍保留此前任务结果。
- 已完成：编辑模式显示原视频和编辑结果的并排预览及下载；分镜模式显示粗剪预览、镜头属性及重投按钮。
- 任务失败：状态事件和错误原因可见；不假装完成，不发布旧镜头为当前版本。
- 任何用户 Prompt/异常消息进入 HTML 对话区前都执行转义，避免脚本注入。
- 会话事件只在当前 Gradio 客户端状态里；刷新浏览器后对话事件未必恢复。后端原有 Job/Project JSON 是真正落盘的事实，不因前端“统一”而合并成同一个持久化模型。
- 上传文件验证/本机监听/一次一项目生成等限制继续沿用原有实现。

## 5. 分阶段计划和落地状态

| 事项 | 本轮 |
|---|---|
| P1 去掉业务级 Tab | 已实现：一个连续页面，两个真实技能按钮 |
| P2 中央对话创作框 | 已实现：附件、主 Prompt、技能切换、单提交入口 |
| P3 动态结果区 | 已实现：编辑前后对比或分镜粗剪，与任务状态对话 |
| P4 分镜区融入项目下游 | 已实现：同页展开镜头资产，独立重投 |
| 统一前端会话 | 已实现：workspace.py，事件与显式路由 |
| 统一后端 Project/资产继承 | 暂缓：需要持久会话、跨任务资产追踪时再设计 |
| Agent 自主规划/多技能注册 | 暂缓：当前没有验证通过的任务编排后端 |
| 原片精准局部编辑/画面一致性 | 暂缓：需要模型能力与真实验收 |

第一阶段前端先统一，不新增 REST 接口，不改现有视频生成后端。第二阶段若需要跨功能承接资产（如“将编辑完的结果直接拆分镜头”），再设计持久的 Workspace ID、素材引用和操作日志；不可把前端的单页视觉误称为已实现的数据继承或 Agent 自主能力。第三阶段逐步加入视频反解、语音/字幕、转场、模型能力验证。

## 6. 测试与验收

1. Gradio 组件中没有两个顶层业务 Tabs；只有一个主输入框和一处生成入口。
2. 视频上传切到编辑技能；模板点击只填充 Prompt，不产生任务调用。
3. Mock 下编辑不可提交，分镜可提交；视频 + 分镜的冲突在前端路由层直接拒绝。
4. 生成事件按状态变化追加，不会每轮轮询重复刷屏。
5. 分镜结果与编辑结果保存在同一 UI 状态对象里，技能切换不丢失已有快照。
6. 分镜逐镜头修改仍走原来的 PATCH + targeted regenerate API。
7. CI 执行 Gradio 构建、路由单测、原有 FastAPI/FFmpeg Mock 与 Omni multipart 协议测试。
8. Windows Git Bash 启动后的首屏视觉与素材交互需要用户实机验收；CI 通过不能替代真实浏览器测试。


## 7. 2026-10-10 上传素材区显示修复

用户 Windows 浏览器截图显示原 `gr.File` 文件条目为低对比度白色方块、文件名及大小几乎不可读：其直接原因是深色创作框和 Gradio 自有的浅色文件卡片混用，且 CSS `.studio-compact-upload *` 对子元素强制浅色文字。

改动：
- 以 `gr.Video(sources=["upload"], format="mp4")` 替换侧栏 `gr.File`，原片上传后可直接播放预览；组件回调仍返回本地 MP4 路径，沿用 upload_changed 和 submit_workspace。
- 素材区宽度不低于 270 像素，避免文件预览被 165 像素窄列挤压；主 Prompt 仍占右侧更大比例。
- 统一主创作框为干净的浅色表面和深色文本，保留紫色能力按钮，杜绝“深色边框套浅色 Gradio 内层、浅色字落到白色文件卡片”的混杂效果。
- 移除 `.studio-compact-upload *` 全局子元素染色，视频内建播放控件由 Gradio 自己决定对比度。
- 保留后端视频大小/长度限制；UI 上传成功不表示 AI 编辑已经生成，Mock 模式仍禁止 V2V 提交。

验收：真实上传 MP4 后能看到视频预览、来源及明显的文字；切换技能时附件状态与冲突提示仍正确。CI 测试检查视频上传组件及 CSS 的危险选择器不存在；用户本机视觉验证仍必须执行。


## 8. Gradio 上传视频与裁剪控件修复（2026-10-10）

用户实机反馈：上传视频后布局高度跳变，点击 Gradio 剪刀后缩略帧下方操作按钮被截断。根因是固定的视频组件 height=198 和上传区 overflow:hidden 冲突。当前修复移除组件自身 height 参数，由 Gradio 根据裁剪内容自行扩展；仅用 CSS 将视频画面固定在约 225px 高，上传组件采用 min-height:318px 预留普通预览空间，并保证上传及创作框 overflow:visible。正常视频画面高度基本保持，剪刀模式需要额外空间时容器允许自然增高，避免强行裁切确认控件。请在 Windows 本机浏览器实际验收。


## 9. 分离视频上传、预览与裁剪（2026-10-10）

用户 Windows 截图多次证明，Gradio 交互式 Video 在狭窄创作框中点击剪刀后，缩略帧和底部确认控件会被截断，即使移除固定高度和 overflow:hidden 仍然复现。因此不再通过 CSS 强制兼容内建剪刀：

1. 主创作框改用紧凑 `gr.File` 上传 MP4，不再因编辑时间轴突然改变主框高度。
2. 独立 `gr.Video(interactive=False, height=208)` 稳定显示视频，无内置剪刀入口。
3. 视频下方「✂ 裁剪视频片段（可选）」折叠区有独立起始/结束时间滑块及“应用裁剪”“恢复原片”按钮；展开占正常页面空间，不会裁切操作按钮。
4. `trim.py` 先由 ffprobe 校验 30 秒/100 MiB，再由 FFmpeg 生成实际 MP4 切片；不覆盖上传的原始视频，支持保留原音轨（若存在）。
5. 前端 `selected_source` 状态决定当前素材，预览和视频编辑提交都读取它，避免裁剪预览与模型提交的输入不一致；“恢复原片”将此状态重新指向上传素材。
6. 即使 Mock 模式不支持 AI V2V，视频裁剪仍可本地执行。以上为真正的剪裁功能，非只改变 UI 播放区间。

后续验收：上传前后创作框保持近似稳定高度；裁剪工具的两个滑块和按钮完全可见；裁剪片段时长确实变短、恢复后复原；如有可用 V2V 服务，确认提交上传的是裁剪 MP4。CI 只可验证 FFmpeg 结果与组件配置，真实 Windows 浏览器仍需回归截图。


## 10. Windows FFmpeg/FFprobe 缺失后的上传体验（2026-10-10）

用户上传 10.6 MB MP4 后，左侧文件条目成功显示，但视频预览出现“错误”标签，并弹出“无法分析视频，请确认已安装 FFmpeg/ffprobe”。根因是 UI 上传回调调用 `inspect_source`，它使用 `ffprobe` 检查片长和视频轨；本机工具不在运行 Gradio 的 Python PATH 中时，子进程抛出 FileNotFoundError，旧版本只给出笼统异常且文件预览的输出状态不一致。

修订：
- `trim.check_media_tools` 显式检查 `ffmpeg` 与 `ffprobe` 的系统 PATH；缺失时提示 Windows PowerShell 的 winget 安装命令、Git Bash 版本检查与重启 Gradio，而不是误报为视频内容出错。
- 上传回调将验证失败变成素材区内的常驻说明，仍显示用户已选择的文件名，但不把未验证的本地 MP4 发给 `gr.Video`，不启用裁剪，也不让未验证原片参与 V2V 请求。
- 上传结果提示放到折叠裁剪面板外，即使不展开也能知道原因。
- 校验通过时继续正常预览、裁剪和后续提交；未改动原有 API 和 FFmpeg 片段处理流程。
- 相关单测同时覆盖全部工具缺失、只有 FFprobe 缺失，以及 UI 清空不可靠预览的回调结构。

恢复指引（Windows PowerShell 安装，Git Bash 验证）：

    winget install --id Gyan.FFmpeg --exact
    # 重新打开 Git Bash，激活 .venv 后
    ffmpeg -version
    ffprobe -version
    python -c "import shutil; print(shutil.which('ffmpeg'), shutil.which('ffprobe'))"

如果命令仍不可用，检查 FFmpeg 的 bin 路径是否已加到 Windows PATH。安装后必须重新启动 Gradio UI；仅刷新浏览器不会重置已启动 Python 进程的环境变量。


## 11. 时间轴可视化、画面标记和实际局部编辑（2026-10-11）

### 原先存在的问题

用户对照即梦的高级编辑截图指出，原来的“开始/结束时间”只有滑块，没有对应视频画面；也不能直接标记视频中的对象并说明修改意图。

### 新交互

- 主创作区下新增宽屏“✂ 时间轴裁剪与画面标记”编辑区，与侧边 MP4 上传控件分离。
- 上传有效视频后，FFmpeg 生成 8 个带时间戳的画面缩略图；单击缩略图可以将它作为起点或终点。起点和终点分别有一张大图，滑动滑块并松开会更新为对应时间帧。
- “✂ 应用裁剪”用 FFmpeg 实际输出新的 MP4；恢复原片和多次裁剪都会更新滑块最大值、播放器和当前上传素材路径。
- 画面标记：选时间点并加载画面，使用 Gradio ImageEditor 画笔或橡皮涂抹目标区域，填写区域修改要求。保存时输出 marked-frame.png 和 annotation.json，后者记录视频时间、归一化 xyxy 框和文字指令。
- 存在真实的“应用本地局部模糊”按钮：在用户选择的起止时间范围内，将单帧标记推导的固定矩形区域通过 FFmpeg crop、boxblur、overlay 处理，输出可下载的 MP4。原片始终保留。
- 标记仅是单帧静态区域，不会跨视频自动追踪人物。标注 JSON 包含 model_mask_consumed=false，明确说明它目前不会被通用 Omni V2V 模型解释为真实的 Mask 条件。
- 改衣服、换人、移除对象等语义级 V2V 区域编辑尚未完成模型能力适配，不会因为画了框就假装模型已执行。需要未来支持空间掩码或标注参考的 V2V 模型和端到端验收。

### 设计边界与验收

- 单页完成上传、看起点/终点、看关键帧条、裁剪、画笔标记、保存标记、局部模糊、下载结果。
- 图层不允许无标记时默认选中全图，必须明确涂抹；错误标记要给出提示。
- 实际裁剪或局部模糊成功后，selected_source 更新为新素材，后续提交模型与播放器使用同一个文件。
- Gradio 组件构建及 FFmpeg 实际输出由 CI 验证；Windows 实机还需交互视觉验收。


### 关键帧交互验收修正

用户点击关键帧时，必须同步更新所选边界滑块和对应 START/END 大图，不能只改数字。保存标记文件同时保存 start/end 时间区间；其中静态框只表示选定帧的矩形范围，生效区间不意味着对象自动跟踪。



## 12. 深色即梦式对话创作框 + 宽屏高级编辑（2026-10-11）

### 用户反馈与本次决策

用户反馈“这个编辑使用起来太复杂了，完全按照即梦的样式改”，参考用户上传的即梦主页创作输入框和“高级编辑”黑色大画布截图。根因不是单个控件位置，而是我们把时间轴、画面标注、局部模糊、导出和参数直接堆到同一页面，任务切换和操作成本过高。

本轮把 UI 调整为**两层式交互**，借鉴用户参考图的视觉层级和操作路径，不复制其品牌或专有资产：

1. **创作首页：** 暗色背景、集中输入框、左侧视频素材预览、一个创作意图 Prompt，底部保留真实支持的视频编辑/视频理解/创作分镜技能和提交入口。素材下面只显示一个“✎ 高级编辑 · 标记画面”，不暴露长时间轴和多按钮参数区。
2. **高级编辑工作区：** 点击高级编辑在当前页面打开独立、接近全屏的暗色编辑面板。标题和关闭按钮置顶，中央是大的可画笔标注的视频帧（Gradio ImageEditor）。画板下方只保留一项当前帧时间及“跳转到这一帧”，底部是一条明显的“描述如何调整画面”文字框和“保存并返回创作”按钮。
3. **次要工具折叠：** 起止时间、关键帧条、真正 FFmpeg 裁剪、恢复原片及本地模糊放到编辑面板的“精确裁剪与本地处理（可选）”折叠区。与即梦图中的直接标记工作流一致：普通用户不必先接触这些参数。
4. **保存闭环：** 点“保存并返回创作”会检查标记与说明，若有涂抹则输出 marked-frame.png + annotation.json（记录时间范围、归一化边界和用户修改要求），将说明回填主 Prompt 并关闭高级编辑。如果只是想写文本、不标记，也可以仅保存指令，不制造假的区域 Mask。
5. **能力边界：** 标注导出、本地裁剪和局部模糊是已接通功能；对运动人物自动跟踪及 AI 语义编辑不是。V2V 需要实际模型能力，不因仅有标注文件就解锁。

### 验收原则

- 不需要在主页面看到超过一个“高级编辑”入口；点击直接进入大画布。
- 画板可使用笔刷，说明可编辑，关闭可不保存，保存后返回创作框且填充文本。
- 未上传 MP4 时打开编辑器会得到明确错误而不是空窗口。
- 精确裁剪和本地模糊可用但默认不展开；保留原始输出、元数据下载与此前 FFmpeg 测试。
- CSS 和 Gradio 布局用真实组件事件，避免仅绘制不可点击的“仿即梦”静态图片。
- 黑色编辑区可容纳完整画板工具条与保存按钮，Windows 本机视觉/画笔体验需最终实测。


## 12. 即梦式简化交互（2026-10-11）

根据实际使用反馈，宽屏弹层虽然已经上线，但默认画面和时间轴操作分离仍不够直观。本轮重新收敛成：主界面只上传、描述和选技能；「高级编辑」弹层默认展示大画面标注画板、画面下方可点击缩略帧、底部提示词与「保存并返回创作」。点击某帧会同步画板和当前标注时间，旧图层不应被误用。裁剪、固定区域模糊以及文件导出仍在折叠的次级选项。当前不是即梦官方 UI 的像素复制，不包含其未公开的模型服务或账号系统。画笔只产生可保存的参考标注；语义级区域替换仍需支持 Mask 的 V2V 模型，不能宣称保存标记即完成重绘。
